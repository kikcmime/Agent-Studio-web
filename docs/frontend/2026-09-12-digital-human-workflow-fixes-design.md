# 数字人页面与运行链路修复设计

## 背景

数字人页面当前存在四类互相关联的问题：列表内容超过视口后无法滚动；进入「编排」后 React Flow 发生无限更新；带查询参数刷新时出现 hydration mismatch；从数字人卡片点击「运行」后，运行台不一定选中刚才点击的流程。此外，本地数据库内 14 个 Agent 仍使用服务端已经下线的 `deepseek-v3.1-ksyun`，导致实际执行返回 404。

## 修复目标

- 数字人列表可以正常纵向滚动，左侧目录在滚动时保持可用。
- 任意数字人均可进入编排页，不再出现 Maximum update depth exceeded。
- 带 `app`、`asset`、`flow`、`mode` 参数直接访问或刷新时，不产生服务端与客户端首屏不一致。
- 点击某个数字人的「运行」后，首页运行台准确选择该流程，而不是默认选择第一条。
- 本地现有 Agent 与新增 Agent 默认使用 `openai-compatible / glm-5.2`。
- 模型不存在等运行错误以可理解的信息反馈，同时保留足够的诊断上下文且不泄露密钥。

## 设计

### 1. 页面滚动

保留桌面外壳的固定视口，只让数字人内容区域承担纵向滚动。移除 `.agent-hub-page` 对内容滚动的阻断，并让目录栏在内容滚动时保持稳定。其他应用页面的溢出策略不受影响。

### 2. 编排器状态稳定性

`useFlowGraphEditor` 的初始化 effect 依赖了每次渲染都会重新创建的函数，effect 执行后调用 `setNodes`，从而触发下一次渲染并形成循环。修复方式是用 `useCallback` 稳定运行状态和图编辑操作；React Flow 的 `nodeTypes`、`edgeTypes` 依赖只使用稳定函数和标量值，避免每次渲染重新注册节点类型。节点选择器的 effect 也改为精确依赖，避免无意义的重复订阅。

### 3. URL 与 hydration

React state 的首个值不再在 lazy initializer 中读取浏览器 URL。服务端和客户端都先使用相同默认值，挂载后再统一从 URL 恢复工作区状态。URL 写回只在恢复完成后启用，避免默认值先覆盖原查询参数。

### 4. 运行目标传递

从数字人卡片点击「运行」时清除当前资产编辑态，并在 URL 中保留目标 `flow`。首页运行台加载已暴露流程后优先选择 URL 指定的流程；目标不存在或未暴露时才回退到主流程或第一条流程。普通页面状态同步不得误删首页运行态的 `flow` 参数。

### 5. 模型迁移与错误提示

更新本地后端 `.env` 的默认模型、示例配置和种子数据默认值，并将本地 PostgreSQL 中现有 14 个 Agent 的模型迁移到 `glm-5.2`。迁移以明确 SQL 文件保留，可重复审查。模型调用失败时，后端返回包含 provider/model 的安全错误摘要；前端继续展示运行失败事件，不展示 API Key 等敏感配置。

## 验证

- 先补回归测试，确认修复前能复现关键失败，再实施代码修改。
- 前端执行类型检查和生产构建；后端执行相关单元测试。
- 浏览器验证：首页进入数字人列表、滚动到底部、分别进入编排和运行、刷新带参数页面，控制台无无限更新与 hydration 错误。
- 数据库核对所有 Agent 的 provider/model；实际发起一次 `glm-5.2` 流程运行并确认可以得到成功事件或真实业务错误，而非模型 404。

## 非目标

- 不重新设计数字人页面视觉样式。
- 不改变流程定义、团队编排含义或斗地主业务规则。
- 不引入新的模型供应商或额外基础设施。
